Скіл QA · правка без git

Хочеш щось змінити в скілі - скопіюй промт

Git-команд знати не треба. Промт нижче пояснює твоєму Claude Code усе: яка гілка, що можна, що ні, і чим закінчити. Твоя частина - описати правку своїми словами і сказати «так», коли він покаже, що вийшло.

Промт

Працюй у теці скіла shopify-testomat-agent. Я мануальний QA, git-командами не володію: роби все сам, а мене питай тільки про суть правки.

Що треба знати про репо:
- адреса betterme-dev/shopify-testomat-agent, моя роль Write;
- у гілку main пушити заборонено: правило організації вимагає pull request з одним апрувом;
- свій PR апрувити не можна, апрув просимо в каналі #qa-ecom-team.

Зроби по порядку, не питаючи дозволу на кожен крок:
1. Перевір ремоут: має бути https://github.com/betterme-dev/shopify-testomat-agent.git. Якщо стоїть стара адреса bttrm-qa-lab - переціль.
2. git switch main і git pull. Гілку заводь від свіжого main: merge-комітів усередині PR бути не повинно.
3. Назва гілки латиницею, з типу і суті: fix/slider-step-1440, docs/onboarding-typo, feat/case-template.
4. Внеси правку, яку я описую нижче.
5. Поясни простими словами, що саме зміниться. Діфф показуй, тільки якщо я попрошу.
6. Після мого «так» закоміть і запуш гілку.
7. Відкрий pull request. Назва і опис - англійською. Назва у форматі "type: short summary", де type це feat, fix, docs, chore, ci або refactor. Опис заповни за шаблоном репо (.github/pull_request_template.md): What changed, Why, How to verify. Постав лейбл, що відповідає типу.
8. Дай мені посилання на PR і готовий текст для #qa-ecom-team з проханням апрувнути.

Якщо щось не виходить - поясни простими словами, що саме зламалось і що потрібно від мене. Не лишай гілку незапушеною і нічого не пиши в main.

Моя правка:

Відкрий Claude Code у теці скіла, встав промт і допиши в кінці, що саме треба змінити. Наприклад: «у файлі docs/40-runbooks/onboarding-new-qa.md у кроці 3 неправильна назва змінної» або «додай у чеклист пункт про перевірку порожнього кошика».

Що станеться далі

  1. Claude сам заведе окрему гілку - твої правки не зачеплять робочу версію скіла.
  2. Внесе зміну і перекаже своїми словами, що саме вийшло. Тут читаєш і кажеш «так» або «ні, не те».
  3. Після «так» запушить гілку і відкриє pull request.
  4. Дасть посилання і текст для #qa-ecom-team - кидаєш його в канал, щоб хтось апрувнув.

Руками, без промта

Якщо з git на «ти» - шлях той самий, тільки команди свої. Гілку називаємо з суті правки: fix/slider-step-1440, docs/onboarding-typo, feat/case-template.

git switch main && git pull
git switch -c fix/коротка-назва
# правимо
git add -A
git commit -m "Що змінено і навіщо"
git push -u origin fix/коротка-назва
gh pr create --base main --fill

Назва і опис PR - англійською. Назва у форматі type: short summary, де type це feat, fix, docs, chore, ci або refactor. Опис заповнюється за шаблоном, який GitHub підставить сам: What changed, Why, How to verify. Лейбл ставимо той, що збігається з типом у назві.

Гілку заводимо від свіжого main - merge-комітів усередині PR бути не повинно. При злитті тиснемо Squash and merge: у головну гілку їде один охайний коміт замість усіх проміжних.

Без gh посилання на створення PR друкує сам git push - досить відкрити його в браузері. Якщо клон ще зі старою адресою, спершу переціль ремоут:

git remote set-url origin https://github.com/betterme-dev/shopify-testomat-agent.git

Чого не треба: качати ZIP замість git pull, комітити локально в main, правити .state/ - це журнал агента, його веде сам агент.

Чому саме так, а не просто зберегти файл

Репо живе в організації betterme-dev, і там діє правило компанії: у головну гілку нічого не потрапляє без pull request і одного апрува. Правило однакове для всіх - для мене теж. Воно й рятує: зламати робочий скіл правкою з гілки неможливо.
